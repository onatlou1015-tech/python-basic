A Syntax Errors vs. Logic Errors – The Two Types of Bugs

All errors fall into two categories: syntax errors (the computer can't understand you) and logic errors (the computer does what you said, but it's not what you meant).

❌ Syntax Errors (Compile-time errors)

These are like grammar mistakes in human language. The computer can't even start your program because it doesn't understand what you wrote.

# Missing colon if age > 18 # SyntaxError: Expected ':' print("Adult") # Missing closing quote print("Hello) # SyntaxError: EOL while scanning string literal # Using a keyword as a variable if = 5 # SyntaxError: invalid syntax # Missing parenthesis print "Hello" # SyntaxError: Missing parentheses # Incorrect indentation def greet(): print("Hello") print("World") # IndentationError: unexpected indent

🐛 Logic Errors (Runtime errors)

These are much trickier. Your program runs perfectly—no syntax errors, no crashes—but it produces the wrong answer. The computer is doing exactly what you told it to do, but what you told it isn't what you meant.

# Mistake 1: Wrong calculation def calculate_rectangle_area(length, width): return length + width # Should be * not + print(calculate_rectangle_area(5, 3)) # Returns 8, should be 15 # Mistake 2: Off-by-one error numbers = [1, 2, 3, 4, 5] total = 0 for i in range(1, len(numbers)): # Wrong! Starts at index 1 total += numbers[i] print(total) # Wrong: 14 (missing the first number) # Mistake 3: Wrong condition def is_eligible_for_senior_discount(age): return age > 65 # Should be >= 65 print(is_eligible_for_senior_discount(65)) # Returns False, should be True # Mistake 4: Using = instead of == def check_password(password): if password = "secret": # Assignment, not comparison! return True return False

The difference at a glance:

Aspect Syntax Error Logic Error
Program runs? No Yes
Computer understands? No Yes
Easy to find? Usually Can be very hard
Error message? Yes, clear No, just wrong output
Example Missing colon Adding instead of multiplying

B Debugging Strategies – Finding the Invisible

Debugging is the art of finding and fixing errors. It's a skill that takes practice, but there are proven strategies that work.

Strategy 1: The Print Statement Method (Your Best Friend)

The simplest and most powerful debugging tool is print(). Insert print statements to see what's happening inside your code.

# With print statements - Finding the bug def calculate_average(grades): print(f"Debug: Starting calculation with {grades}") total = 0 print(f"Debug: Initial total = {total}") for grade in grades: print(f"Debug: Adding {grade} to total") total + grade # This is the bug! Should be += print(f"Debug: Current total = {total}") print(f"Debug: Final total = {total}") result = total / len(grades) print(f"Debug: Result = {result}") return result # Output shows total never changes → Aha! The bug is found!

Strategy 2: Rubber Duck Debugging

Explain your code, line by line, to an inanimate object (like a rubber duck). Often, just verbalizing what the code should do reveals the problem.

# "Duck, I'm going to explain what this code does..." def is_palindrome(text): reversed_text = text # Wait... I'm assigning reversed_text to the original text! # Then I'm modifying text? No, I'm modifying reversed_text? # Actually, text[::-1] is what I need! # The fix: return text == text[::-1]

Strategy 3: The "Divide and Conquer" Method

When you have a large program and don't know where the bug is, use print statements to narrow it down.

# Use print statements between each step def complex_processing(data): print("DEBUG: Entering complex_processing") result1 = step_one(data) print(f"DEBUG: After step_one: {result1}") result2 = step_two(result1) print(f"DEBUG: After step_two: {result2}") result3 = step_three(result2) print(f"DEBUG: After step_three: {result3}") return result3 # The last print that shows the expected value identifies where things go wrong

Strategy 4: The "Simplest Case" Method

Test your code with the simplest possible data. If it works, gradually make it more complex until it breaks.

# Test with simplest case print(calculate_average([10, 10])) # Should be 10 # Then add more cases print(calculate_average([10, 20, 30])) # Should be 20 # Then edge cases print(calculate_average([])) # What should this return?

Strategy 5: Check Your Assumptions

Often, bugs come from false assumptions about what data looks like.

# Assumption: User will always enter a number age = int(input("Enter your age: ")) # User enters "twenty" → ValueError! # Better: Validate and handle errors try: age = int(input("Enter your age: ")) except ValueError: print("Please enter a valid number!") age = 0 # Assumption: List has items grades = [] average = sum(grades) / len(grades) # ZeroDivisionError! # Better: Check first if grades: average = sum(grades) / len(grades) else: average = 0

D Code Review – The Power of Fresh Eyes

Code review is the process of having another person (or yourself after a break) look at your code to find bugs, suggest improvements, and ensure quality.

Self-Review Checklist:

✅ Does the code work?
✅ Is the code readable?
✅ Is the code DRY?
✅ Is the code efficient?
✅ Is the code robust?
✅ Are variables named clearly?
✅ Is there appropriate whitespace?
✅ Are comments helpful?

Args: n (int): Non-negative integer Returns: int: n! (n * (n-1) * ... * 1) Example: >>> factorial(5) 120 """ if n < 0: raise ValueError("Factorial is not defined for negative numbers") result = 1 for i in range(1, n + 1): result *= i return result def calculate_average(numbers): """ Calculate the average of a list of numbers. Args: numbers (list): List of numbers Returns: float: The average, or 0 if list is empty Example: >>> calculate_average([10, 20, 30]) 20.0 """ if not numbers: return 0 return sum(numbers) / len(numbers)

📌 Golden Rules Summary

The 5 Golden Rules of Debugging:

  • Read the error message carefully. It tells you what's wrong and where. Don't panic—error messages are your friends.
  • Use print statements to track variables. Print values at key points. Print before and after operations to see what changed.
  • Test in small pieces. Build incrementally, test often. Break complex problems into smaller parts.
  • Check your assumptions. What do you think is true? Prove it. Print data types and contents.
  • Take a break. Step away for 5 minutes. Fresh eyes find fresh bugs.
